## Deep dives and technical write-ups

- Nolan Lawson benchmarks twelve JavaScript frameworks by what an AI agent spends building the same app — The author had Claude Code (Opus 5.5, high effort) build one Pokémon app five times in each of twelve frameworks (three runs for Angular), tested against a spec-conformance suite and Lighthouse. Median cost ran from $2.67 (Hono+htmx) to $4.97 (Angular), and lines of code from 1,370 to 2,009. Lighthouse performance and accessibility scores were nearly saturated, so the differences sit in cost, tokens and JavaScript bytes (0 KiB for Astro against 142 KiB for Next.js). Framework-supplied MCP servers and skills were often ignored by the agents: Nuxt's was never used, and Next.js's skill files were read in 1 of 5 runs. For anyone choosing a stack because it is "better for agents", this is a measurement where there were only claims. The author states the caveats himself: one content-style app, high run-to-run variance, Lighthouse biased against single-page apps. The benchmark code is on GitHub. Author: Nolan Lawson, web performance engineer and blogger · Format: deep dive (benchmark investigation) · Length: about 17 min. Source: https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/

- Robert Haas, PostgreSQL committer: Postgres 19 is late because LLMs are finding bugs faster than humans can fix them — Haas compares the same April-to-September window across years. Commits to the master branch were roughly flat or slightly down, but back-patched commits to the release branch rose by more than 60% (724 to 1,169), and commits back-patched to at least one earlier release rose by more than 74% (248 to 433). Three large features were reverted late in beta (FOR PORTION OF, SQL/PGQ and partition MERGE/SPLIT), and the release is likely to slip into November. His reading is that LLM-assisted bug reports, not sloppier committers, explain the surge. He admits the causal story is inferred from commit counts and from what the committers experience. A rare account, with numbers, of what AI-driven bug-finding costs a mature open-source project. Author: Robert Haas, PostgreSQL major contributor and committer (post also published on Neon's blog) · Format: essay with data · Length: about 6 min. ## Essays and arguments

- Frank Calegari, in a guest post on Terence Tao's blog: "Mathematics has changed. Let's act like it" — Calegari argues that OpenAI's 6 October release of more than 700 research papers is a watershed, that mathematicians should stop treating it as an attack on the subject, and that the profession should change what it rewards: judge papers on ideas and exposition rather than on results a machine could produce, hire through interviews rather than publication lists, publish fewer and better papers (even pausing journals if boards cannot adapt), and record Lean-checked autonomous proofs as part of the body of knowledge. He also says the OpenAI papers are poorly written, break attribution norms and are sometimes wrong, and quotes Hugo Duminil-Copin's lament that every major open problem he named was claimed solved. This is one mathematician's proposal, not a consensus; Calegari notes that the post was converted from another file format using AI. The most substantial argument this week about what AI does to a knowledge profession's incentives. ## Prompting and context techniques

- Armando Picón: give agent decisions a durable home and specify the next behaviour with acceptance cases — Picón argues that agents can take on more implementation work while engineers still own what to build and what evidence suffices. His practical technique: keep architectural decisions, with their reasons, in a short reviewable file (his example is a PROJECT_GUIDE.md covering scope and exclusions, system boundaries, quality commands and links to deeper decisions) because long sessions get summarised and the summary can keep the conclusion but lose the condition that justified it. Before each increment, give the agent the relevant files plus the intended change, constraints and acceptance cases, and ask for a paraphrase to catch misunderstanding. He marks his search-screen example as hypothetical, notes that a file has no special power unless the tool loads it, and says any claim of token savings needs a measurement of the whole task. No benchmark is offered, so this is a practitioner's method, not tested evidence. Author: Armando Picón, software engineer · Format: essay · Length: about 7 min. Source: https://picon.dev/en/publications/ai-assisted-engineering/

- r/PromptEngineering thread: when the same prompt works one day and fails the next, test it repeatedly and pin the model version — The original poster says the cause was sampling variance plus a prompt that only succeeds when the model takes the right path, and fixes it with an explicit format, a worked example and a constrained output structure. A top reply adds a second cause, that an alias such as "latest" can point to a different model snapshot, and suggests pinning the dated version, running the same input 5 to 10 times and counting passes (9 of 10 says more than one good run). Anecdotal, but the method is cheap to try. Author: Reddit users (original poster and reply) · Format: forum thread · Length: about 3 min. Source: https://old.reddit.com/r/PromptEngineering/comments/1xj8o66/why_my_prompt_worked_yesterday_and_failed_today/
