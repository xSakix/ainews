## Deep dives and technical write-ups

- NVIDIA's Reshard collective cuts the cost of pushing fresh weights from training GPUs to inference GPUs in RL post-training — During reinforcement learning, the policy is updated on training GPUs and must be copied to separate inference GPUs after every update ("refit"). NVIDIA estimates the payload at about 10 TB per refit for today's largest open-weight models. The write-up replaces gather-and-broadcast with a direct sharded transfer that moves only the theoretical minimum of data between any two parallelism layouts, with an open-source reference implementation (NCCL M2N Reshard, in the nccl-extensions repository). In NeMo RL benchmarks on DGX H100 and GB200 with Qwen 3 235B and DeepSeek v3 671B it reports 2.7x to 5.7x faster refit. These are NVIDIA's own numbers, and a hybrid is used (Reshard for the large feed-forward weights, the old path for small ones). Worth reading for anyone training or post-training large models, because refit is one of the hidden costs of RL at scale. Author: Youngeun Kwon, Kaushik Kandadi Suresh, Sreeram Potluri, Terry Kong and Sangkug Lym, NVIDIA engineers · Format: deep dive · Length: about 15 minutes Source: https://developer.nvidia.com/blog/accelerating-reinforcement-learning-weight-refit-with-the-reshard-collective/

- parse_number() as a SQLite extension, C against Rust — Simon Willison had Claude (Opus 5.5 in chat) build four versions of a function that turns strings such as "-$1,234.56" or "12.5%" into numbers. The first plain C version lost to Rust on decimals because it leaned on strtod(), Rust's equivalent was about twice as fast, and a compact hand-written decimal fast path in C closed the gap. Per row, over 2 million rows, mixed data cost 19 ns for the optimized C version, against 41 and 46 ns for the two Rust extensions and 67 ns for the first C version. The C binary is 14 KB against roughly 300 KB for Rust. The write-up shows the two prompts that did the work (ask for the comparison, then ask the model to beat the faster implementation) and the 8 million fuzz checks used to confirm that all versions agree. A small, reproducible example of using a model as a benchmarking partner, with the code in the linked research report. Author: Simon Willison, independent developer and writer · Format: deep dive (short research note) · Length: about 4 minutes Source: https://simonwillison.net/2026/Nov/8/sqlite-parse-number-c-vs-rust/

- How NVIDIA runs a team of agents over its own GPU clusters — NVIDIA describes the AI Factory Operations Agent it uses on DGX SuperPOD clusters: specialised sub-agents (job recovery, hardware, observability, Kubernetes, cluster management, research) talk over MCP, correlate failures across compute, network, hardware and scheduling layers, and answer SREs in a chat interface. It runs fully on premises on locally served Nemotron open models. The lessons it lists are concrete: clear agent boundaries, read-only investigation first to earn trust, precise MCP tool definitions, and visible reasoning so an engineer can check the evidence before acting; per-tenant sandboxes isolate customer data. It is a vendor write-up with no incident-level numbers, so treat the benefits as NVIDIA's claim; the design lessons are the value. Author: Kavya G Y and Rohan Adwankar, NVIDIA · Format: engineering write-up · Length: about 10 minutes Source: https://developer.nvidia.com/blog/how-nvidia-uses-ai-agents-to-streamline-ai-factory-operations/

## Essays and arguments

- Agent memory needs a shared format, argues the maker of one memory tool — The author lists the memory shapes now on a typical machine (AGENTS.md and CLAUDE.md files, Cursor rules, Anthropic's memory tool, GitHub Copilot Memory, Letta blocks, Mem0, LangGraph's store, the MCP memory server, Graphiti) and notes that none can read the others. His argument is that observability had the same fragmentation before 2019 and fixed it by agreeing a data model, naming conventions, a protocol and reference code (OpenTelemetry), and that agent memory should do the same now while formats are young and a neutral home (the Linux Foundation's Agentic AI Foundation, which already hosts MCP and AGENTS.md) exists. He states that he builds one such tool (LoreKit, open source) and that its format is only one proposal. The comparison table of forgetting rules and addressing across the tools is the useful part, and the essay is the author's opinion. It pairs with Anthropic's memory components post from 6 November (already covered). Author: Mads Thines (per the page's author tag; he says he works on OpenTelemetry at Dash0 and builds LoreKit) · Format: essay · Length: about 8 minutes Source: https://www.lorekit.io/blog/open-agent-memory-format

- Writing is a thinking tool, and with LLMs it becomes a widening advantage — Murat Demirbas argues from Manuel Blum's remark (a finite automaton becomes a Turing machine once it has paper and pencil) that writing is external memory for thought, like out-of-core execution. His claim about LLMs is that a six-page memo no longer proves that thinking happened, because a model can produce the pages without it, so people who still draft themselves keep a comparative advantage; he gives five working rules (draft in bulk, edit hard, plain style, write for yourself, schedule it). It is a personal essay without data, and it is relevant to readers asking what to keep doing by hand. Author: Murat Demirbas, computer scientist and long-time blogger · Format: essay · Length: about 10 minutes Source: http://muratbuffalo.blogspot.com/2026/11/writing-as-thinking-tool.html

- "Coherence arguments" for AI goal-seeking mix two different claims — Steven Byrnes takes the market argument (agents with circular preferences get money-pumped) and argues it contains two claims that are usually fused: pressure to be self-consistent, which is real in markets, in self-modifying AI and in training algorithms, and pressure to care only about long-run outcomes with ruthless indifference to anything else, which he finds weaker and more contingent. He offers human within-lifetime learning, which builds economies while also caring about norms and self-image, as a probable existence proof that the first does not force the second. It is a conceptual argument, not an experiment; it matters because much safety reasoning about agents depends on the stronger claim. Author: Steven Byrnes, AI safety researcher · Format: essay · Length: about 20 minutes (3,200 words) Source: https://www.alignmentforum.org/posts/5a4tuSNDNodPsiS26/some-coherence-arguments-are-two-different-things-in-a

## Prompting and context techniques

- A work queue in git to stop agent context-switching — Sergey Kuhne (reached 135 comments on Hacker News on 8 November) describes his fix for juggling 20 Claude Code or Codex tabs. Every ticket is a markdown file in the repo; an agent works the board in cycles (researches new tickets, builds those a human tagged safe, runs tests and a browser check, never deploys to production, builds on a branch and asks first for sensitive code); a script collects everything that needs a human judgement into one prioritised "owner inbox", shown as one page rebuilt from git on every cycle; his verdict goes back onto the ticket in git, which closes the context. The claim that it lowers fatigue is his own report with no measurement, and he says the hard parts are fast context loading and tickets blocked on a ruling only he can give. Techniques to try: keep the state in files rather than chat, route all human decisions through a single queue, make closing a ticket an explicit act. Author: Sergey Kuhne, developer · Format: practitioner write-up · Length: about 4 minutes Source: https://sergeykuhne.com/blog/fighting-ai-brain-fry

- A two-layer rules file for coding assistants, refined by commenters — An r/PromptEngineering poster reports changes to a personal rules file after a week of comments: a short stable base file plus a few project lines; a line moves into the base only after it proves useful in a second project; project lines are trimmed with the question "would I want this on every project?"; two lines kept permanently ("if it's unclear, list your assumptions before answering", "if you're not sure, ask before you build"); one question at a time. Evidence is anecdotal and the account appears to promote a related product, so read it as a starting point, not a result.
