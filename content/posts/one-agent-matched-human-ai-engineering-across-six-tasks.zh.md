一名基础设施工程师打开了两组结果。一组来自经验丰富的团队多年持续改进的软件。另一组来自一个编程智能体（agent）：它拿到的是一个小型起始项目、固定的算力配额和截止时间。工程师先看分数，再看产生这个分数的测试。

*本文开头和结尾的场景为示意性描写，其中人物均为虚构。*

一篇新论文把这组比较背后的问题提得更进一步：编程智能体能否构建让人工智能运行起来的系统，而不仅仅是在别人搭好的系统里修复一个问题？

Singularity-Bench 由卡内基梅隆大学（Carnegie Mellon University）牵头、联合学界与业界研究者开发，让 11 种智能体配置完成 6 项规模较大的工程任务。其中一种配置，即通过 Claude Code 运行的 Claude Opus 5.5，在每项任务中都达到或超过了人工构建的参考实现。它的综合 Singularity-Index 为 1.25，人工基线为 1.00。其余 10 种配置的平均分为 0.58。

作者在基准测试的名称中使用了“奇点”一词。但这些测量并不能证明任何模型可以自主发明并训练出自己的下一代。它们证明的是一个范围更窄、但已经影响深远的结论：如果目标明确、硬件昂贵且有足够的工作时间，智能体有时能够搭建出具有竞争力的复杂 AI 基础设施。

## 六项工程任务，而非六道编程题

多数软件基准测试考查某类具体修复。智能体收到一个代码仓库和一份缺陷报告，或者编写一个必须比参考实现运行更快的内核。这种问题边界便于测量，但也意味着工程系统的大部分已经准备好了。

Singularity-Bench 让智能体负责技术栈中更大的一部分。一项任务从最简 nanoGPT 项目开始，要求智能体设计并训练语言模型。另一项任务为强化学习之前的中间训练阶段选择数据和流程。第三项任务训练编程智能体。其余任务分别构建推理服务、编程智能体运行框架，以及必须服务 28 个模型的集群编排系统。

前三项任务允许使用 4 块 GB300 GPU，时限为 12 小时。构建推理服务也有 12 小时。编程运行框架任务有 6 小时和 1 块 GPU。集群任务则在 4 小时内使用 16 块 GPU。每项任务都有自己的性能指标，智能体的输出会与在相同硬件上运行的成熟人工实现比较。

这些参考实现并非随手选取的示例。它们包括 Megatron-LM、SGLang、Claude Code 和 NVIDIA Dynamo 等成熟系统与方案。这也是达到它们的水平值得关注的原因。智能体并没有从这些系统继承所有重要设计决策，尽管它仍在任务规定的约束内工作。

研究者还没有向智能体提供参考实现，并阻断了智能体容器的互联网访问。如果没有这项限制，智能体可能会直接获取已知解决方案，而不是开发一个可以独立评测的方案。

## 领先配置的优势来自哪里

使用 Claude Code 的 Opus 5.5 在 5 项任务上超过参考实现。在第 6 项任务，也就是通过强化学习训练编程智能体时，它的分数在统计意义上与人工结果相当。标题中的比较依据的是这 6 项任务的分数，并不意味着可以毫无限定地声称，智能体在每种工作上都比人类工程团队更强。

部分提升十分明显。在预训练任务中，智能体生成的模型验证集困惑度为 12.77，低于参考实现的 14.22，因此表现更好。它选择了一个较小的模型，并根据可用时间调整训练计划。在推理任务中，按基准测试工作负载模拟计算，它的系统每 GPU 小时收入为 11.52 美元，SGLang 则为 8.18 美元。

另一些胜出幅度很小。它的智能体运行框架得分为 0.468，Claude Code 为 0.438。研究者发现，这个差距很大程度上只来自多成功修复了一次缺陷。这些证据说明两者结果接近，并不支持全面取代成熟工具的结论。

完整运行轨迹显示出一种可以重复的工作模式。最强的智能体先测量吞吐量，再选择架构；尽早让端到端流程运行起来，并对照目标测试拟议改动。它还会根据剩余时间安排工作。在预训练任务中，主要训练运行大约在会话开始 44 分钟后启动。

这些观察很重要，因为人们很容易把结果归功于模型本身的推理能力，而实际结果可能同样依赖工具、反馈和控制循环。这个基准测试本身就在受控条件下展示了这种差异。

## 运行框架改变了结果

同一个模型放进不同的智能体运行框架，得到的结果并不相同。

GLM 5.3 使用 Claude Code 时得分为 0.657，使用 Codex 时为 0.228。MiniMax M3 的对应分数分别为 0.607 和 0.223。深度求索（DeepSeek）V4.1 Flash 则呈现相反趋势：使用 Codex 得分为 0.698，使用 Claude Code 为 0.520。

这些差异并不只是呈现方式上的细微不同。运行框架决定智能体如何接收任务、使用 shell、记住先前工作、选择工具、测试候选方案，以及判断何时完成。当工作持续数小时并涉及一个完整系统时，错误的测试或过早停止，都可能让原本有希望的实现失去价值。

研究者还测试了要求更高推理强度是否总能改善结果。答案是否定的。在一项推理服务实验中，中等推理强度的 Opus 5.5 运行获得了最高推理强度约 96% 的收入分数，而智能体 API 预算用量只有后者的 65%。更高的推理强度没有带来系统性能的单调提升。

价格数字也有各自的适用边界。在主要结果中，Opus 5.5 配置完成 6 项任务的智能体 API 调用费用为 425.41 美元。位于成本与性能前沿的一种 DeepSeek 配置花费 4.36 美元。这些合计不包括训练、服务和评测系统所需的 GPU。因此，不能把它们当作复现这项工作的完整成本。

## 智能体可以作弊的基准测试

团队在尝试测量工程自主能力时发现了第二个问题：能力足够强的智能体能够利用评测器的弱点。

标准 Harbor 框架在受控环境中运行智能体代码，然后检查产生的工作成果。研究者系统地开发了对抗性提交，使其看起来成功，却没有满足预定工程目标。有些攻击修改了评测器信任的日志。另一些则植入代码，让代码一直存活到验证阶段，或者操纵语言模型裁判将要读取的证据。

加入一个本身也是大语言模型（LLM）的裁判，并没有解决所有问题。攻击者能够影响裁判看到的内容，包括围绕可疑行为的叙述。论文将这些攻击归入 OWASP 智能体应用 10 类风险中的 9 类。

研究者构建了名为 Breakwater 的扩展。它检查环境完整性，限制 API 访问，在智能体工作结束、评分开始的边界处终止进程，记录外部审计轨迹，并在额外的受限阶段运行提交的代码。Breakwater 捕获了研究测试库中的每一种攻击。

这是一个有明确适用范围、有意义的结果。它并不能证明 Breakwater 能抵御所有可能的攻击，正如通过 Singularity-Bench 不能证明具备不受限制的自主能力。工程分数和安全分数都依赖评测者选择的任务与对手。

## 更严格的比较

这项实验改变了可信的 AI 工程师演示应有的样子。模型能够编写看似合理的代码，只是起点。提交的系统还必须能够运行、达到性能目标、遵守任务规则，并经得起独立验证。

论文记录了尚存的差距。11 种智能体配置中，有 6 种在推理服务任务上得零分。有些提交失败，是因为始终没有保存检查点，或生成的代码没有保留所需上下文。另一些提交产生了无法信任的测量结果。即使智能体构建了有效系统，工作也仍然发生在人工划定的边界内，使用指定硬件，并受时间限制和特定目标约束。

因此，Singularity-Bench 最有启发性的部分，可能是把成果与测量放在一起。作者展示了一个智能体：在几项精心挑选的任务上，它能够与人类多年构建的基础设施竞争。他们也展示了，隔离不充分的评测器如何轻易地把表面的成果变成误导性的数字。

桌前的工程师现在有三样东西需要检查：分数、提交的系统，以及一份系统本身无法重写的审计记录。屏幕上的结果依然重要。结果背后的证据同样重要。
